# Documentation

- Keep current behavior, target design, and historical migration evidence
  visibly distinct. Code, versioned contracts, frozen manifests, and tests are
  authoritative for what is implemented.
- `plans/` contains proposed, historical, or pending work. A checked box or old
  handoff statement is not implementation evidence; update the status banner or
  index when code overtakes a plan.
- `curricula/` describes target capability progression and may include unbuilt
  levels. Do not register or expose a task family solely because it appears there.
- Architecture docs must state P/Q measure, numeraire, state, units, day count,
  numerical method, and permission boundary when those are material.
- Use repository-relative links and update inbound/outbound links when moving a
  document. Do not duplicate the same normative rule across many documents;
  point to the owning contract or local README.
